# AWS SAA-C03 Concepts — aligned to the exam guide

The four section names follow the exam guide's design domains (Secure 30%, Resilient 26%, High-Performing 24%, Cost-Optimized 20%). The study repository's service-family modules are source material; concepts are summarized and placed under the closest exam task.

## Content Domain 2: Design Resilient Architectures

### Messaging and Event Processing — Task 2.1

- Amazon SQS FIFO queues // A FIFO queue requires a MessageGroupId and preserves message order within each group; different groups can be processed concurrently, and deduplication supports exactly-once processing semantics. Create it with a .fifo suffix (a Standard queue cannot be converted in place); in the cited throughput model, four-message batches provide 1,200 messages per second, up to 300 per second without batching or 3,000 with batching.
  - Batching // SQS batch API calls carry up to 10 messages, reducing request overhead and multiplying effective message throughput; in the cited FIFO example, four messages per call provide 1,200 messages per second to meet a 1,000-per-second need. Keep throughput within the queue quota, which in that example is 300 messages per second without batching and 3,000 with batching.
- Amazon SQS standard queues // Standard queues provide virtually unlimited throughput with at-least-once delivery and best-effort ordering, so duplicates or reordering are possible; choose them when scale matters more than strict order. Messages can be up to 1 MiB and are retained for 4 days by default, configurable from 1 minute to 14 days; Lambda can poll them in batches through an event source mapping.
- Amazon SQS buffering // SQS durably decouples producers from consumers and absorbs traffic bursts or consumer outages, letting workers process queued messages at their own pace and retry work until it is deleted or retention expires. It is useful for asynchronous, failure-tolerant jobs; separate queues let workers prioritize one class of work by polling its queue first.
- Amazon SQS dead-letter queue (DLQ) // A redrive policy moves messages to a dead-letter queue after they exceed the configured receive-count threshold, isolating repeatedly failing work for diagnosis or later redrive. Use a DLQ with the same queue type as its source and set the threshold to distinguish persistent failures from transient retries.
- SQS queue-based Auto Scaling // Scale queue consumers using backlog per instance, commonly visible messages divided by the number of InService instances, and target tracking to maintain a chosen backlog. Choose the target from processing capacity and acceptable queueing delay so the fleet can drain surges without overprovisioning.
- Multi-stage SQS workflow // Put a separate SQS queue between independently scalable processing stages so each stage can absorb a backlog without blocking the others. Scale each worker fleet from its own queue depth, preserving work while downstream processing catches up.
- AWS Lambda SQS event source mapping // A Lambda event source mapping polls an SQS queue and invokes the function with messages in batches, scaling serverless processing without application-managed pollers. Messages are removed after successful processing; failures can be retried after the visibility timeout, so handlers should be idempotent.
- Amazon SNS // An SNS topic fans each published message out to its subscribers, and subscription filter policies can select messages using attributes or JSON bodies; CloudWatch alarms can publish alerts to a topic. If Lambda subscribers are throttled because account concurrency is exhausted, increase available Lambda concurrency or request a quota increase rather than scaling SNS servers.
- S3 EventBridge notifications // Enable a bucket's EventBridge integration to send supported S3 events to an event bus, then use JSON event-pattern rules to route them to multiple target types. EventBridge can also archive matching events and replay them for reprocessing when those features are configured.
- SQS message visibility timeout // After a consumer receives an SQS message, the visibility timeout hides it from other consumers while it is processed; delete the message on success or extend the timeout for longer work. The default is 30 seconds and the maximum is 12 hours; if the message is not deleted before expiry, it becomes visible again and may be processed again.
- DynamoDB Streams // DynamoDB Streams captures item-level inserts, updates, and deletes and preserves modification order for each item; records are retained for 24 hours and can be consumed with Lambda. Use Kinesis Data Streams for DynamoDB when longer retention or more flexible stream-consumer patterns are required.
- CloudWatch Logs subscriptions // A subscription filter forwards matching CloudWatch Logs events in near real time to Lambda, Kinesis Data Streams, or Data Firehose for processing or delivery. For cross-account streaming, configure a destination with an access policy and the required role so the source account can deliver events.
- EventBridge archive and replay // An EventBridge archive stores all events or those matching an event pattern from an event bus for a configured period or indefinitely. Replay selected archived events back to the bus to let downstream rules and targets reprocess them.
- S3 Event Notifications versus EventBridge // S3 Event Notifications send selected object events directly to Lambda, SQS, or SNS and support key-prefix or suffix filters. Choose EventBridge when you need richer JSON event-pattern filtering, more target choices, or archive and replay; enable the bucket's EventBridge integration first.
- SQS long polling // Long polling makes ReceiveMessage wait up to 20 seconds for a message, returning as soon as one is available and reducing empty responses, API calls, and request cost. It is preferable to short polling for cost-efficient retrieval from queues that are often empty.
- Amazon MQ // Amazon MQ is a managed Apache ActiveMQ or RabbitMQ broker that supports familiar protocols such as AMQP and MQTT, allowing compatible existing applications to migrate with minimal messaging-code changes. Choose it when broker compatibility is important; SQS and SNS are different cloud-native messaging models rather than drop-in broker replacements.
- SQS delay queues // A delay queue hides newly sent messages from consumers for a configured delay of up to 15 minutes, postponing their first delivery. This differs from a visibility timeout, which starts only after a consumer receives a message.
- SQS temporary queues // The Temporary Queue Client multiplexes many application-managed virtual queues onto one physical SQS queue, reducing API calls and improving throughput for request-response workloads with sparse traffic per virtual queue. It automatically cleans up unused virtual queues, saving application and deployment effort compared with managing a physical queue per request.

## Content Domain 1: Design Secure Architectures

### IAM and Application Security — Tasks 1.1–1.3

- IAM permissions boundary // A permissions boundary is a managed policy that caps the permissions an IAM user or role can exercise; effective permissions are the intersection of the boundary and the entity's identity-based permissions, and the boundary grants nothing by itself. Boundaries apply to users and roles, not groups, and prevent broader attached policies from expanding effective access beyond the cap.
- IAM least privilege // Grant only the actions needed on the narrowest resource ARN: for S3, s3:ListBucket uses the bucket ARN (arn:aws:s3:::example-bucket), while s3:DeleteObject or s3:GetObject uses the object ARN pattern (arn:aws:s3:::example-bucket/*). Separate bucket-level and object-level permissions so a policy authorizes the intended operation without granting unrelated access.
- Cross-account IAM role // An IAM role's trust policy is its resource-based policy and specifies which principals may assume it; its permissions policies specify what the resulting session can do. A user or service assumes a role for temporary credentials, and cross-account S3 access through a Lambda execution role requires both the role's permissions and the bucket policy to allow access.
- IAM policy `aws:SourceIp` condition // The aws:SourceIp condition matches the source address of the API request as AWS observes it, not the public or private address of a resource being created. CIDR conditions can allow or deny caller IP ranges, including excluding one address, and can be combined with a separate aws:RequestedRegion condition.
- IAM groups // Attach a permissions policy to an IAM group and add or remove users to manage their shared access centrally; each user receives the group's permissions in addition to their own applicable policies. Groups cannot be nested and are not principals that can sign in or be assumed.
- API Gateway resource policy // An API Gateway resource policy controls who can invoke an API using principals and supported conditions such as source IP; an explicit deny for addresses outside an allow list can restrict callers. API Gateway is not placed in a customer subnet, so a security group cannot be attached to the API endpoint itself.
- Cross-account access credentials // Use STS AssumeRole to obtain short-lived credentials for an authorized cross-account role instead of sharing long-lived IAM user keys; the role trust policy controls who can assume it and its permissions policy controls the session's actions. For cross-account S3 access through a Lambda execution role, the role policy and bucket policy must both allow the request.
- IAM database authentication // For supported RDS MySQL and PostgreSQL databases, IAM database authentication replaces a stored password with a SigV4 authentication token valid for 15 minutes; the client presents the token as its password over TLS. The workload, such as Lambda, needs an IAM role with rds-db:connect permission and the database must have IAM authentication enabled.
- AWS WAF rate-based rule // A WAF rate-based rule counts requests using its configured aggregation key and can block requests that exceed the configured rate, protecting supported resources such as CloudFront, ALB, and API Gateway. Attach it to the application entry point to curb abusive high-rate traffic without changing the application.
- Amazon Cognito // Cognito User Pools provide an app user directory for sign-in, MFA, and federation; they authenticate users but do not themselves grant direct AWS resource credentials. Identity Pools exchange authenticated or guest identities for temporary AWS credentials through IAM roles when clients need authorized direct access to AWS resources.
- AWS Directory Services selection // AWS Managed Microsoft AD provides a managed native Microsoft AD that can establish trusts with on-premises AD; AD Connector proxies authentication to an existing directory without storing directory data in AWS. Simple AD is a Samba-based directory for compatible workloads and cannot establish a trust with on-premises Microsoft AD.
- IAM Roles for Service Accounts (IRSA) // IRSA associates an EKS Kubernetes service account with an IAM role through the cluster's OIDC provider, so Pods using that account obtain temporary AWS credentials. Use separate service accounts and narrowly scoped role policies to give different workloads distinct AWS permissions rather than sharing the node role.
- IAM policy `aws:RequestedRegion` condition // The aws:RequestedRegion condition key compares the Region targeted by an API request, not the caller's geographic location or the resource's physical location. Use it to allow or deny actions only in specified AWS Regions, such as permitting RunInstances only in eu-west-1.
- AWS WAF IP match rule // A WAF IP match statement compares a request's source address with an IP set and can allow, count, or block matching traffic. Use it to block requests from a known malicious IP at a protected web application or API.
- API Gateway HTTP API JWT authorizer // An HTTP API's native JWT authorizer validates bearer tokens from a configured OIDC issuer and can enforce audience and route-scope claims without custom Lambda authentication code. It is a low-latency, lower-cost fit for APIs that need standard JWT validation and claim-based authorization.
- Amazon S3 bucket policy // A bucket policy is a resource-based JSON policy attached to an S3 bucket that can name principals in the same or another account and grant bucket or object actions. Cross-account access requires authorization from the bucket's resource policy and the external principal's account-side permissions, with explicit denies taking precedence.
- IAM Identity Center permission sets // Permission sets define the AWS permissions provisioned as IAM roles in assigned accounts for users and groups in IAM Identity Center. Integrate the center with the enterprise directory, map groups by job function to least-privilege permission sets, and manage federated access centrally instead of creating individual IAM users.

## Content Domain 3: Design High-Performing Architectures

### VPC and Hybrid Networking — Task 3.4

- Internet Gateway connectivity // For IPv4 internet connectivity, attach an Internet Gateway, route internet-bound traffic to it, assign the instance a public IPv4 address or Elastic IP, and permit the traffic in security groups and network ACLs; the gateway translates public IPv4 addresses. A public address alone is insufficient, and ping also requires ICMP rules.
- PrivateLink // PrivateLink lets a consumer reach a provider service without public routing or VPC peering: the consumer creates an interface endpoint, and the provider exposes the service through a Network Load Balancer; an RDS database itself cannot be directly exposed and needs an NLB-backed proxy. DataSync can send on-premises NFS data to EFS through its interface endpoint over a private Direct Connect VIF, including on a daily schedule.
- S3 gateway VPC endpoint // Gateway endpoints provide private VPC access to S3 and DynamoDB without an internet or NAT gateway and have no additional endpoint charge; associate the endpoint with route tables and control access with endpoint, IAM, or resource policies. Cognito Identity Pools can separately exchange authenticated identities for temporary, scoped AWS credentials when users need S3 access.
- NAT Gateway high availability // A public NAT Gateway in a public subnet, associated with an Elastic IP, lets private-subnet instances initiate internet connections but blocks unsolicited inbound connections. For AZ resilience, place one NAT Gateway in each used AZ and route each private subnet through its same-AZ gateway.
- VPC peering // VPC peering privately connects two VPCs using private IPv4 or IPv6, including across Regions, if their CIDRs do not overlap; it is non-transitive. EC2 instances in a peered VPC can access EFS through its mount targets when routing, DNS, security groups, and NFS access are configured.
- AWS Transit Gateway // Transit Gateway is a managed hub for routing among VPCs and on-premises networks, with reachability controlled by attachment and route-table configuration; it avoids a peering mesh and can centralize shared-services access. It connects to Direct Connect through a transit VIF and supports ECMP over multiple dynamically routed Site-to-Site VPN tunnels.
- AWS Global Accelerator // Global Accelerator provides two static anycast IPv4 addresses and routes TCP or UDP over the AWS global network to healthy regional endpoints such as ALBs and NLBs, reducing internet-path latency and enabling health-based regional failover. Endpoint weights and traffic dials can shift deployment traffic without DNS-cache delays, and the fixed addresses simplify firewall allowlists.
- AWS Resource Access Manager (RAM) subnet sharing // AWS RAM lets accounts in the same AWS Organization share VPC subnets, so their resources can use a centrally managed VPC and communicate privately without separate peering links. This reduces duplicated network resources and operations when shared placement is the goal.
- AWS Direct Connect Gateway // A Direct Connect Gateway is a global resource that connects Direct Connect virtual interfaces to virtual private gateways in multiple Regions, or to a Transit Gateway through a transit VIF, subject to allowed prefixes and association limits. It provides hybrid connectivity to those VPCs but is not itself a VPC-to-VPC transit router; use Transit Gateway for direct transitive routing among many VPCs.
- Direct Connect public VIF // A public virtual interface advertises public AWS service prefixes over Direct Connect, allowing on-premises systems to reach public AWS endpoints such as S3 without sending data across the public internet. Use a private VIF to reach private VPC addresses through a virtual private gateway.
- Direct Connect private VIF // A private virtual interface connects Direct Connect to a VPC through a virtual private gateway, or through a Direct Connect Gateway for multi-Region designs. It can carry on-premises traffic to a PrivateLink interface endpoint, such as DataSync’s EFS endpoint; use a public VIF for public S3 endpoints.
- Transit Gateway VPN ECMP // Transit Gateway can use equal-cost multi-path routing across multiple dynamically routed Site-to-Site VPN tunnels to aggregate throughput beyond a single tunnel’s 1.25 Gbps maximum. A virtual private gateway does not provide Transit Gateway ECMP, and adding tunnels without dynamic routing and ECMP does not provide the same aggregate path.
- Private IP for same-VPC/AZ workloads // Use private IPs for communication between workloads inside the same VPC, including same-AZ traffic, so it stays on private AWS network paths rather than taking an unnecessary public route. Public addresses are for internet-reachable endpoints, not a requirement for internal communication.
- Amazon CloudFront // CloudFront is a content delivery network for cacheable or dynamic HTTP(S) content, such as S3-hosted static files; edge caching reduces latency and offloads application servers, but CloudFront is not a general UDP accelerator. Separately, an IAM permissions boundary caps permissions granted to a user or role and cannot be attached to a group; that access-control feature is unrelated to CloudFront.
- Route 53 private hosted zone prerequisites // For every VPC associated with a Route 53 private hosted zone, enable both enableDnsSupport and enableDnsHostnames so the Amazon-provided VPC resolver can answer private-zone queries. Creating the zone or records without both settings does not make those names resolvable.
- Amazon EFS cross-account access // A file-system resource policy can authorize a workload in another account to mount EFS, while VPC sharing or peering provides network reachability to an EFS mount target. Configure an EFS access point in the Lambda mount settings to provide the intended root directory and POSIX identity without copying the data.

## Content Domain 3: Design High-Performing Architectures

### EC2, Load Balancing, and Scaling — Task 3.2

- EC2 Instance Store // Instance Store is high-performance, host-attached block storage suited to cache, scratch, and other data that can be recreated or replicated; it is ephemeral and cannot be detached and moved to another instance. Its data is not preserved when an AMI is created, so do not use it as the sole copy of durable data.
- EC2 user data // EC2 user-data scripts run as root and, by default, execute on first boot only; configure cloud-init or another mechanism if they must run on later boots. User data is useful for launch-time setup, such as attaching an Elastic IP with API permissions from an instance role, but is not a substitute for an image containing static software.
- EC2 reboot alarm action // A CloudWatch alarm can invoke the EC2 reboot action when an instance status check fails, requesting a reboot without EventBridge and Lambda polling. The recover action is different: it is intended for system status-check failures on supported EBS-backed instances.
- EC2 Auto Scaling Standby // Put an Auto Scaling instance into Standby to remove it from load-balancer service while keeping it in the group for maintenance, then return it when ready. If health checks could trigger an unwanted replacement, suspend only the ReplaceUnhealthy process during the work.
- Auto Scaling `ReplaceUnhealthy` process // When replacing an unhealthy instance, Auto Scaling terminates it before launching its replacement; AZ rebalancing instead launches replacement capacity before terminating instances. Suspend ReplaceUnhealthy when maintenance must prevent health-check-triggered replacement.
- Auto Scaling health checks // An Auto Scaling group uses EC2 health checks by default; enable load-balancer health checks when an unhealthy application target should trigger replacement, and allow a grace period after launch. ALB health checks can fail because the path is wrong or the target security group blocks the ALB; a multi-AZ group behind an ALB can replace failed web instances.
- Predictive scaling // Predictive scaling uses historical patterns to forecast recurring demand and schedules capacity ahead of peaks. Combine it with a dynamic policy such as target tracking to respond to unexpected real-time changes.
- Target tracking vs. step/scheduled scaling // Target tracking adjusts capacity to keep a metric near a chosen target, such as EC2 or ECS CPU utilization; step scaling responds in increments to alarm thresholds. Scheduled scaling handles known time-based demand, predictive scaling forecasts recurring demand, and a queue-backlog metric can drive worker target tracking.
- Spot request types // A one-time Spot request is fulfilled once, while a persistent request can be reopened after interruption; stopping a Spot Instance does not reopen its request until it is started. Spot is lower-cost interruptible capacity, so use it for work that tolerates interruption and can be retried.
- Canceling a Spot request // Canceling a Spot request prevents future fulfillment or replacement but does not automatically terminate an already running Spot Instance. Cancel the request and terminate the instance separately when both are required.
- Spot Fleet // Spot Fleet requests a target capacity of Spot Instances and can replace capacity after interruptions; Auto Scaling groups can also use Spot capacity from a launch template to scale a stateless tier. For interruptible asynchronous jobs, pair Spot workers with SQS so queued work survives worker interruption and can be retried.
- Application Load Balancer (ALB) path routing // An ALB is a Layer 7 HTTP(S) load balancer whose listener rules route by path, host, headers, method, query string, or source IP; *.example.com matches test.example.com but not example.com. HTTPS listeners support SNI to select certificates by hostname and Cognito User Pool authentication before forwarding; AWS WAF can also protect an ALB.
- Network Load Balancer (NLB) // An NLB is a Layer 4 TCP, TLS, UDP, or TCP_UDP load balancer and can provide static IPs for SSH or fixed-IP allowlists. It can target EC2 by primary private IP, use health checks, register on-premises IP targets, and route only to targets in its Region; a public NLB can front private instances. A public NLB can expose SSH on port 22 to an Auto Scaling bastion fleet, while Global Accelerator can use regional NLBs as endpoints for global anycast entry and routing.
- Cross-zone load balancing // When enabled, a load balancer distributes requests evenly across targets in all enabled AZs; ALB enables it by default. When disabled, each NLB node sends its share only to targets in its AZ, so traffic is split by AZ rather than evenly by instance; NLB, GWLB, and CLB disable it by default.
- ECS Service Auto Scaling // ECS Service Auto Scaling changes the desired number of running tasks using service metrics such as average CPU or memory utilization. Target tracking can maintain a chosen utilization target as load changes, scaling task count rather than the EC2 cluster alone.
- ECS/EKS with Fargate // Fargate runs ECS tasks or EKS Pods without managing EC2 workers, and ECS on Fargate can mount EFS for persistent shared files. Use a managed stream such as Kinesis Data Streams for ingestion and Fargate for long-running container processing beyond Lambda’s 15-minute maximum.
- EC2 tenancy // Dedicated Instances run on hardware dedicated to one AWS customer and generally cost less than Dedicated Hosts when host-level placement and license visibility are unnecessary. Dedicated tenancy can be inherited from the VPC or selected at launch, so either setting produces dedicated instances.
- EC2 cluster placement group // A cluster placement group packs EC2 instances close together within one AZ for low latency and high throughput in tightly coupled HPC workloads. Spread and partition groups prioritize failure isolation instead.
- EC2 Elastic Fabric Adapter (EFA) // An Elastic Fabric Adapter provides enhanced networking with OS-bypass communication for tightly coupled HPC and machine-learning workloads. It complements ENA networking to reduce latency and improve inter-instance communication beyond a standard ENI or public IP.
- Detailed CloudWatch monitoring // EC2 detailed monitoring publishes metrics to CloudWatch at one-minute intervals instead of the five-minute basic interval. It does not collect operating-system logs; use the CloudWatch agent to forward log files before Auto Scaling terminates an instance.
- Amazon Machine Image (AMI) sharing and copying // An AMI can be shared with another AWS account or copied to another Region for launches there. Copying an AMI backed by an encrypted snapshot cannot produce an unencrypted target snapshot; encryption must be preserved or changed to another encrypted key.
- EC2 instance recovery // A CloudWatch recover action can move a supported EBS-backed instance to healthy hardware after a system status check failure, preserving its instance ID, private and Elastic IP addresses, metadata, and public IPv4 address. It does not preserve in-memory state, does not apply to instance-store-backed instances, and is distinct from a reboot action for an instance status check failure.
- Auto Scaling termination policy // The default termination policy first selects an AZ with the most instances, then generally terminates an instance using the oldest launch template or launch configuration in that zone. This can rebalance group capacity independently of unhealthy-instance replacement.
- Kubernetes Cluster Autoscaler // The Cluster Autoscaler detects Pods that cannot be scheduled for lack of resources and adjusts the EC2 Auto Scaling group that supplies EKS worker nodes. It scales node capacity to satisfy pending Pod requests rather than scaling only from a cluster-wide CPU alarm.
- Systems Manager patching behind a load balancer // Systems Manager Automation can use AWSEC2-PatchLoadBalancerInstance to deregister or drain an instance, wait for in-flight requests, patch it, and register it again. A Maintenance Window schedules this controlled workflow so the instance is not serving traffic during patching.
- Aurora Serverless v2 capacity scaling // Aurora Serverless v2 automatically adjusts Aurora database capacity for variable or intermittent demand while retaining Aurora relational compatibility. Pair it with an EC2 Auto Scaling group behind an ALB when both application and MySQL-compatible database tiers must scale with reduced server administration.
- Aurora MySQL read scaling and availability // An Aurora MySQL cluster can place writer and reader instances in different AZs; readers offload read traffic while Multi-AZ design improves database availability. Combine it with an ALB and multi-AZ Auto Scaling group when the web tier also needs elasticity and failure tolerance.
- Amazon RDS Multi-AZ failover // RDS Multi-AZ maintains a synchronous standby in another AZ for high availability and automatic failover; the standby is not a read-scaling replica. An ALB and multi-AZ Auto Scaling group address web-tier traffic distribution and instance failure separately from database failover.
- CloudWatch Logs agent on EC2 // The CloudWatch agent can stream EC2 log files to CloudWatch Logs while an instance is running, preserving diagnostic evidence if Auto Scaling later terminates it. Detailed EC2 monitoring publishes metrics at a higher frequency but does not collect log files.

## Content Domain 4: Design Cost-Optimized Architectures

### Storage, Backup, and Data Protection — Task 4.1

- EFS Infrequent Access // EFS Standard-IA is the lower-cost EFS storage class for files not accessed every day, with storage pricing up to 92% lower than EFS Standard; it retains the shared, POSIX/NFS file-system interface and makes data immediately available to concurrent clients. Choose it when infrequently used files still need file semantics and fast access, rather than object storage such as S3.
- Amazon FSx for Windows File Server // A fully managed Windows file system that provides SMB shares, NTFS permissions, and Active Directory integration to Windows and SMB-capable Linux clients. Choose it for shared Windows-compatible files, including applications that need SMB or Windows ACLs and Microsoft DFS namespaces that organize shares into a single folder structure spanning hundreds of petabytes.
- AWS Storage Gateway File Gateway // A hybrid file service that presents on-premises applications with NFS or SMB shares backed by Amazon S3, while caching frequently accessed data locally for low-latency reads. Use it to retain existing file protocols while placing durable, scalable objects in S3, where lifecycle rules can tier cold data.
- AWS Snowball Edge // Use a Snowball Edge device to move very large datasets when network transfer is impractical, or to run supported compute at edge sites with limited connectivity. For archival imports, the device loads data into S3 first; use an S3 lifecycle rule to transition it to Glacier or Deep Archive, because Snowball does not transfer directly into those archive classes.
- S3 lifecycle rules // Lifecycle rules automatically transition eligible S3 objects to supported storage classes or expire them according to age, prefix, tags, or other configured filters; for example, use a prefix rule to move image objects to Standard-IA after 45 days, transition data to Glacier after 180 days, or expire objects four years after creation. They can move Snowball imports to Deep Archive with a zero-day threshold, but transitions only follow supported paths: no class can transition back to Standard, and One Zone-IA cannot transition to Standard-IA or Intelligent-Tiering; lifecycle rules do not make objects immutable.
- S3 Standard-IA // S3 Standard-IA is for infrequently accessed objects that still need millisecond retrieval and multi-AZ resilience; retrieval charges and a 30-day minimum storage duration apply. A lifecycle policy can transition objects into it after 30 days and expire them at a configured age (for example, four years); choose it over Glacier when data must be available immediately, and over One Zone-IA when data is not readily recreatable.
- S3 Glacier retrieval classes // S3 Glacier Instant Retrieval serves archived objects in milliseconds (with a 90-day minimum); Flexible Retrieval restores in about 1–5 minutes expedited, 3–5 hours standard, or 5–12 hours bulk (90-day minimum), while Deep Archive restores in about 12 or 48 hours (180-day minimum). Use the slower, lower-cost Deep Archive tier for long-term backups, and import data into S3 before lifecycle-transitioning it to an archive class.
- One-time S3 bucket copy // Use `aws s3 sync` for a straightforward one-time copy of objects between buckets, including copying only new or changed files on subsequent runs. Use S3 Batch Replication instead when existing objects must be copied under S3 replication semantics; ordinary sync is not a substitute for ongoing replication.
- Shared storage for load-balanced applications // Move uploads off instance-attached EBS and into storage shared by the application fleet: use EFS when shared POSIX file access is needed or S3 Standard for object storage. Either keeps a user’s files available whichever load-balanced EC2 instance handles the next request; archive classes are unsuitable for active serving.
- Amazon FSx for NetApp ONTAP // A managed NetApp ONTAP file system that can serve the same data to Windows, Mac, and Linux clients over SMB and NFS. Choose it when mixed operating systems and both file protocols must share data with minimal file-server administration.
- EBS Snapshot Recycle Bin // The EBS Snapshot Recycle Bin retains deleted EBS snapshots according to retention rules, allowing recovery from accidental deletion before permanent removal. Configure a seven-day retention rule to protect snapshots while still expiring them automatically, rather than preventing all deletions.
- Amazon S3 Storage Lens // S3 Storage Lens provides organization-wide visibility into S3 usage, activity, and storage metrics; advanced metrics and recommendations add per-bucket details such as versioning status for dashboards across Regions. Use it to find buckets missing a configuration at scale rather than building custom inventory processing.

## Content Domain 3: Design High-Performing Architectures

### Databases, Analytics, and Migration — Tasks 3.3 and 3.5

- Amazon ElastiCache for Redis // ElastiCache for Redis is a managed in-memory data store for sub-millisecond, read-heavy or rapidly changing workloads such as leaderboards, shared sessions, and current location lookups. Redis data structures support sorted-set rankings and geospatial commands, while key expiration (TTL) can remove stale entries; this is a general-purpose application cache/store, unlike DAX, which is tied to DynamoDB.
- DynamoDB Accelerator (DAX) // DAX is a managed, in-memory cache designed specifically for DynamoDB that can return hot reads with microsecond latency and reduce repeated reads against a busy table. It is largely transparent to DynamoDB applications, unlike a general-purpose ElastiCache layer that typically requires application cache logic; it does not cache relational databases or S3 objects.
- Amazon Athena // Athena is a serverless SQL query service that reads data in place from S3, commonly using schemas registered in the Glue Data Catalog, so ad hoc checks need no database cluster or ETL load. Partitioning, compression, and columnar formats reduce the amount scanned and therefore query cost; use it for SQL analysis of raw files or transcripts rather than as an operational database.
- Amazon Neptune // Neptune is a purpose-built, managed graph database optimized to store billions of relationships and query highly connected data with millisecond latency, such as traversing social-network links to find friends and their content. It is a better fit for relationship-centric traversals than forcing graph questions into relational joins, a warehouse, or a full-text search index.
- Aurora Serverless // Aurora Serverless is a managed relational Aurora configuration that automatically adjusts database capacity with demand, making it suitable for unpredictable or intermittent OLTP workloads without sizing a fixed DB fleet in advance. Aurora supports MySQL- and PostgreSQL-compatible engines and managed high availability, so it remains a relational database rather than a NoSQL store or cache.
- AWS DMS Serverless // AWS DMS Serverless automatically provisions and scales replication capacity as migration or replication demand changes, avoiding manual sizing of a replication instance. It supports an initial load plus ongoing change data capture (CDC), such as synchronizing an on-premises Oracle source with RDS for Oracle.
- AWS SCT and DMS // For a heterogeneous database migration, AWS Schema Conversion Tool (SCT) converts schema objects and code that need changes for the target engine, while AWS Database Migration Service (DMS) moves the data and can replicate ongoing changes with CDC. SCT is not generally required for a homogeneous engine migration, and DMS alone does not convert incompatible schema or stored-procedure code.
- Babelfish for Aurora PostgreSQL // Babelfish lets Aurora PostgreSQL understand supported portions of SQL Server T-SQL and the SQL Server wire protocol, reducing application changes during migration. It is not complete SQL Server equivalence: use SCT to convert schema and unsupported objects, and DMS to move data.
- Amazon Redshift cold-data offload // Keep infrequently queried historical data in S3 and query it with Athena when ad hoc SQL access is still needed, instead of paying to retain all cold data in a continuously available warehouse. This separates low-cost object storage from active analytics compute; it does not make Athena a Redshift storage tier.
- Amazon DynamoDB // DynamoDB is a fully managed, serverless NoSQL key-value and document database that scales horizontally and delivers single-digit millisecond access for high-volume lookups such as GPS records. It is an operational primary datastore rather than a cache; per-item TTL can expire records such as analytics results after a defined retention period.
- Amazon Transcribe // Amazon Transcribe automatically converts speech in audio recordings into text. Use it to produce searchable transcripts from customer-service calls, then query transcript data in S3 with Athena; Transcribe performs speech recognition, not SQL analysis.
- Amazon Comprehend sentiment analysis // Amazon Comprehend uses managed natural-language processing to identify sentiment in text, such as customer feedback, without operating a custom NLP model. In an asynchronous feedback pipeline, queue API submissions and let Lambda call Comprehend before storing the results.
- Amazon ElastiCache for Memcached // ElastiCache for Memcached is a managed, distributed in-memory cache that supports multithreaded, multi-core nodes for caching relational query results. It is nonpersistent and does not provide Redis-style replication-based high availability, so choose it for parallel cache throughput rather than durable data or Redis-specific features.

## Content Domain 2: Design Resilient Architectures

### Serverless Web and Content Delivery — Task 2.1

- Lambda and API Gateway // AWS Lambda runs code on demand for up to 15 minutes, scales with events or requests, and has a default regional concurrency quota of 1,000 that can be raised; provisioned concurrency pre-initializes environments to reduce cold starts. API Gateway fronts HTTP backends with stateless REST/HTTP APIs or stateful, full-duplex WebSocket APIs; REST API usage plans pair API keys with client-specific throttling rates and quotas, and response caching reduces repeated backend calls for read-heavy endpoints, and S3 object-created notifications can invoke Lambda to process uploads such as image thumbnails.
- EventBridge scheduled rule // An EventBridge rule can invoke targets such as Lambda on a recurring rate or cron schedule, including weekly jobs, without an always-running scheduler host. Use it for event-bus rules with scheduled patterns; EventBridge Scheduler is the dedicated service for flexible high-scale schedules and direct integrations such as ECS tasks.
- Lambda layers // A Lambda layer packages reusable libraries, runtimes, or other dependencies that can be attached to multiple functions, avoiding duplicated deployment bundles. Use layers for shared code; they do not themselves schedule, trigger, or scale functions.
- VPC-enabled Lambda internet access // A Lambda function not attached to a customer VPC can reach public endpoints by default; attaching it to private VPC subnets does not automatically provide internet egress. Route public internet traffic through a NAT Gateway, or use a VPC endpoint for supported AWS services that can be reached privately.
- Lambda monitoring // Use CloudWatch alarms on Lambda metrics such as ConcurrentExecutions and Invocations to detect sudden scale or traffic spikes and respond to cost or capacity concerns. Because Lambda can scale quickly, metric alarms provide visibility that is not available from assuming traffic grows gradually.
- Amazon EventBridge Scheduler // EventBridge Scheduler is a managed, serverless service for one-time or recurring rate- and cron-based schedules, without maintaining a cron host. A schedule can invoke an ECS task running on Fargate, which suits containerized scripts and long-running jobs better than Lambda’s 15-minute execution limit.
- Amazon EventBridge event bus // EventBridge event buses receive events from AWS services, applications, or supported SaaS partners and route matching JSON events to targets through rules. This decouples event producers from consumers and is especially useful when services or SaaS applications should react to each other without direct calls.

## Content Domain 4: Design Cost-Optimized Architectures

### Cost and Operations — Tasks 4.1–4.4

- Compute Savings Plans // A Compute Savings Plan applies discounts in exchange for a committed hourly spend across eligible EC2, Fargate, and Lambda usage, with more flexibility than an EC2 Instance Savings Plan. It does not cover SageMaker; pair it with a separate SageMaker Savings Plan when both compute types need commitment discounts.
- SageMaker Savings Plans // A SageMaker Savings Plan discounts eligible SageMaker machine-learning usage in exchange for a committed hourly spend. It is separate from Compute Savings Plans, which cover eligible EC2, Fargate, and Lambda usage, so both commitments may be needed for broad coverage.
- AWS Budgets Savings Plans coverage budget // An AWS Budgets Savings Plans coverage budget monitors the percentage of eligible usage covered by Savings Plans and can notify stakeholders when coverage falls below a configured threshold. It provides a purpose-built alert without custom billing reports or CloudWatch cost estimates.
- AWS CloudFormation // CloudFormation provisions and updates AWS resources from reusable infrastructure-as-code templates, allowing teams to standardize settings such as RDS configurations. Template properties define resource behavior—for example, a security group’s SecurityGroupIngress entries configure inbound rules (such as HTTP from 0.0.0.0/0 and SSH from 192.168.1.1/32), not outbound rules or a network ACL; CloudFormation itself adds no charge, but its resources incur normal charges.
- EBS volume selection // Choose gp2 for general-purpose volumes with size-linked IOPS and burst capability; gp3 provides a 3,000-IOPS and 125-MiB/s baseline with independently provisioned performance, while io1/io2 serve sustained high-IOPS needs (io1 supports up to 64,000 IOPS). EBS charges for provisioned volume capacity rather than only used file space (so a 1-GB file on a 100-GB volume is billed as 100 GB); gp2 can burst to 3,000 IOPS for occasional demand, and HDD types st1 and sc1 cannot be EC2 boot volumes.
- Cost of data egress // Reduce transfer charges by placing chatty analytics clients near their data source so large query results do not cross a Direct Connect or internet link; only the small interface payload may need to travel. For cross-AZ replication, use private IPs to keep traffic on the private AWS network rather than public or Elastic IP paths.

## Content Domain 1: Design Secure Architectures

### Multi-account governance and secure workloads — Tasks 1.1–1.2

- Service Control Policies (SCPs) // SCPs set the maximum permissions available to principals in AWS Organizations member accounts, including account root users, but grant no permissions; they do not restrict the management account and do not apply to service-linked roles. Use an SCP deny as an organization-wide guardrail, for example to prevent member accounts from changing CloudTrail or to block EC2 launches that lack required tags.
- SCP and IAM evaluation // A member-account request must be allowed by IAM and permitted by every applicable SCP in the account’s organization path; an IAM allow cannot override an SCP restriction, and an explicit deny wins. SCPs affect member-account users, roles, and root users, but not service-linked roles.
- AWS Control Tower // Control Tower automates a multi-account landing zone, account provisioning, and ongoing governance through preventive SCP guardrails and detective AWS Config controls, with CloudTrail logging. A shared networking account can host a VPC and use AWS RAM to share its subnets with governed workload accounts.
- AWS CloudFormation StackSets // StackSets use one CloudFormation template to create, update, or delete stacks across selected AWS accounts and Regions in a single operation. They are the cross-account, cross-Region choice for consistent resource provisioning, including across an organization.
- IAM policy evaluation // An IAM request is allowed only when an applicable policy allows it and no applicable policy explicitly denies it; absent an allow, it is implicitly denied. Conditions apply to request context: aws:SourceIp checks the caller’s source address, while EC2 region conditions constrain the target Region, and a negated IP condition can exclude one address within an allowed CIDR.
- AWS shared responsibility model // AWS secures the cloud infrastructure; customers remain responsible for in-cloud identities, data, configurations, and workload controls according to service type
- IAM role for an AWS workload // Attach a least-privilege IAM role to an EC2 instance through its instance profile, or configure the appropriate workload role for services such as Lambda, so the application receives temporary credentials from AWS. This grants access to resources such as S3 or DynamoDB without embedding or rotating long-lived access keys.
- Root user protection // Protect the account root user with a strong unique password and MFA, do not create or share root access keys, and use root only for tasks that require it. Route each account’s root email alias to a monitored central mailbox and set alternate billing, security, and operations contacts to team-managed distribution lists.
- IAM Identity Center federation // IAM Identity Center provides centrally managed workforce SSO across AWS accounts and supported applications by assigning permission sets to users or groups; permission sets contain IAM policies and can use identity attributes for ABAC. It can use an existing directory through AD Connector or AWS Managed Microsoft AD trust, letting directory groups receive least-privilege account access without individually managed IAM users.
- Security groups and network ACLs // Security groups are stateful, allow-only firewalls on network interfaces, so replies are automatic; tiered rules should reference the upstream group, such as public HTTPS to an ALB on 443, ALB to EC2 on 80, EC2 to PostgreSQL on 5432, or web to SQL Server on 1433. Network ACLs are stateless subnet-level allow/deny lists evaluated by ascending rule number, so permit both directions including ephemeral return ports; public reachability also needs an Internet Gateway route and a security-group rule for the protocol (such as ICMP), and an Internet Gateway ID is not a valid security-group source.
- AWS WAF and Shield // AWS WAF web ACLs filter HTTP(S) requests on supported resources such as CloudFront and ALBs, using rules for exploits, geographic or IP matching, and request-rate limits. Shield Standard supplies baseline Layer 3/4 DDoS protection; Shield Advanced adds always-on protection for resources such as ALBs, automated application-layer mitigation, detailed telemetry and reports, and access to the DDoS Response Team.
- AWS Firewall Manager // Firewall Manager centrally applies supported security policies across AWS Organizations accounts, including AWS WAF, Shield Advanced, Network Firewall, and VPC security groups. It enforces consistent policies as in-scope resources are created; threat-detection services such as GuardDuty and Inspector are not firewall-policy targets.
- AWS Systems Manager Session Manager // Obtain auditable shell access to managed instances without opening inbound SSH or maintaining bastion hosts
- IAM Access Advisor and credential report // Access Advisor shows service-last-accessed information for least-privilege reviews; the credential report audits account IAM credential status
- AWS Secrets Manager versus Parameter Store // Use Secrets Manager for managed secret rotation and RDS integration; Parameter Store provides hierarchical, versioned configuration and SecureString values, with advanced-tier policies for expiration or no-change notifications.
- ECS task role // Assign each ECS task a role in its task definition so that the task has workload-specific permissions, separate from the EC2 instance profile used by the ECS agent.
- CloudTrail data events // Enable high-volume resource-level activity such as S3 object reads/writes or Lambda invocations when it must be audited; these events are not logged by default.
- IAM `aws:RequestedRegion` condition // Use this IAM condition key to restrict the AWS Region in which API calls may be made.
- AWS Network Firewall // Managed Layer 3–7 inspection for VPC ingress, egress, east-west, and hybrid traffic; rules can be centrally managed across VPCs with Firewall Manager.
- VPC Flow Logs // Record network-flow metadata at VPC, subnet, or ENI scope, including managed interfaces; send it to S3, CloudWatch Logs, or Firehose for IP/port analysis and ACCEPT/REJECT troubleshooting.
- VPC Traffic Mirroring // Copy selected inbound or outbound packets from source ENIs to an ENI or Network Load Balancer target for inspection; sources and targets can be in peered VPCs.
- CloudFormation service role // Let CloudFormation create, update, or delete stack resources through an IAM service role, so stack users need not hold those resource permissions but must have iam:PassRole.
- Route 53 Resolver inbound and outbound endpoints // An inbound Resolver endpoint lets on-premises DNS resolvers forward queries into a VPC; an outbound endpoint plus forwarding rules sends selected VPC queries to on-premises DNS servers. The directions are distinct and are used for hybrid DNS over connectivity such as VPN or Direct Connect.
- AWS WAF geographic match rule // A WAF geographic match statement allows or blocks HTTP(S) requests according to the request’s country of origin, including when WAF is associated with an ALB. Combine it with an IP set when a policy must also allow or block specific addresses; security groups cannot filter by country.
- Amazon Security Lake // Security Lake automatically centralizes security data from AWS, on-premises, and supported third-party sources in an S3-based data lake, normalized to the Open Cybersecurity Schema Framework (OCSF). It replaces custom collection and normalization pipelines for supported sources.
- AWS Organizations tag policy // Organizations tag policies standardize tag keys and allowed values and report compliance across attached accounts or OUs; they do not by themselves prevent resource creation or guarantee that untagged resources receive a tag. Use SCPs for preventive controls, such as denying EC2 launches without a required tag and denying deletion of protected tags.
- AWS Config managed rules // AWS Config records resource configuration history and evaluates configurations against managed or custom rules to show compliance; rules detect noncompliance rather than blocking API actions. For example, an ACM expiration rule can flag imported certificates expiring within 30 days and notify a team through SNS; ACM-issued certificates are renewed automatically, unlike imported certificates.
- Amazon EFS access control // Control which clients can mount an EFS file system with an IAM policy, and control network reachability to its mount targets with security groups. IAM governs mount authorization and client permissions, while the security group permits NFS traffic (TCP 2049) only from approved clients.
- IAM security best practices // Require MFA for privileged IAM users and use CloudTrail management events to audit IAM actions. Do not share user credentials or grant broad privileges, and give EC2 applications role credentials rather than embedding long-lived keys.
- AWS Managed Microsoft AD // AWS Managed Microsoft AD runs a managed Windows Server Active Directory in AWS for directory-aware workloads such as SQL Server applications and supports trust relationships with an existing on-premises AD for cross-domain authentication and SSO. Unlike AD Connector, it creates a managed directory in AWS rather than merely proxying authentication to an existing directory.
- AWS Systems Manager patch management // Systems Manager Patch Manager automates OS patching for managed instances; Default Host Management Configuration can supply required Systems Manager permissions without replacing each instance role. For load-balanced instances, the AWSEC2-PatchLoadBalancerInstance automation drains an ALB target, patches it, then registers it again, and Maintenance Windows can schedule the workflow.
- EC2 Instance Connect // EC2 Instance Connect injects a temporary public SSH key to establish a connection to an instance, avoiding the need to distribute long-lived SSH keys. A direct console connection uses the instance’s public IP and still requires network reachability and SSH access to be allowed.
- Single-instance EC2 Auto Scaling recovery // An Auto Scaling group spanning multiple Availability Zones with minimum, maximum, and desired capacity set to one can replace a failed monolithic instance in another zone without running two copies continuously. An instance role authorizes the required API calls, and launch user data can associate a preallocated Elastic IP with the replacement.
- Cognito identity pools and private S3 access // A Cognito identity pool exchanges an authenticated user-pool identity for temporary AWS credentials from an IAM role, allowing least-privilege per-user access to S3. An S3 gateway VPC endpoint lets the private-subnet application reach S3 without sending that traffic over the public internet.

### Data security controls — Task 1.3

- AWS KMS envelope encryption // Encrypt bulk data with a data key and protect that data key with a KMS key; KMS direct encryption is for small payloads
- AWS KMS versus CloudHSM // KMS provides managed key operations; CloudHSM offers dedicated, customer-controlled HSM hardware for workloads requiring that control model
- S3 Object Lock Compliance mode // Compliance mode applies WORM retention to an S3 object version: no principal, including the account root user, can overwrite or delete that version until its retention date expires. Explicit version-level retention sets its own retain-until date and is not overridden by a bucket default; use this for immutable, immediately accessible records rather than long-term Glacier vault archives.
- S3 Object Lock Governance mode // Governance mode protects an S3 object version from overwrite or deletion during retention unless a principal has the required permissions and explicitly bypasses governance retention. Unlike Compliance mode, authorized users can override the lock, so it is not the choice when even root must be unable to shorten retention.
- AWS Backup Vault Lock // Enforce WORM retention for backup recovery points so they cannot be deleted or have retention shortened, even by the root user while the lock is enabled.
- S3 Glacier Vault Lock // A Glacier Vault Lock policy enforces compliance controls on archives in an S3 Glacier vault and can be locked against future policy changes, making it suitable for low-cost long-term WORM retention. It is separate from S3 Object Lock and AWS Backup Vault Lock, and does not provide the immediate access of an S3 object for audit records.
- S3 SSE-KMS Bucket Keys // S3 Bucket Keys reduce requests from S3 to AWS KMS for SSE-KMS objects and can lower KMS request costs by up to 99 percent while retaining KMS-backed encryption and key control. They use a bucket-level key to reduce per-object KMS request traffic; they do not switch encryption to SSE-S3.
- KMS multi-Region keys // A KMS multi-Region primary key and its regional replicas share key material and key ID, so replicated ciphertext can be decrypted in another Region without re-encrypting or making a cross-Region KMS call. Each replica is managed as a regional key, and a single-Region key cannot be converted into a multi-Region key; create a new key and re-encrypt or replicate accordingly.
- RDS encryption at rest // RDS encryption with AWS KMS protects database storage and snapshots; an existing unencrypted DB instance cannot be encrypted in place, so copy an encrypted snapshot and restore a new instance. Encrypted snapshots can be shared cross-account by sharing the snapshot and authorizing the recipient to use the KMS key, and Multi-AZ RDS provides managed failover for supported engines such as SQL Server.
- RDS SSL/TLS // Use SSL/TLS for the connection between an application and RDS, such as PostgreSQL, to encrypt database traffic in transit and validate the server certificate. It does not encrypt stored database files or replace database authentication and authorization.
- CloudFront Origin Access Control (OAC) // Use CloudFront Origin Access Control with a private S3 REST origin and a bucket policy that authorizes the distribution, preventing direct public-origin access; the legacy Origin Access Identity is another CloudFront-only access pattern. OAC can sign supported origin requests, including uploads, while viewer-IP filtering belongs in AWS WAF; for a CloudFront custom domain, the ACM certificate must be in us-east-1.
- CloudFront signed URLs and signed cookies // CloudFront signed URLs grant time-limited access to an individual private object, while signed cookies authorize access to multiple restricted files without changing each URL. Both rely on a trusted signer and do not replace HTTPS for encrypting traffic in transit.
- AWS Certificate Manager and CloudFront // An ACM certificate used for a custom domain on a CloudFront distribution must be requested or imported in us-east-1, even when the distribution serves users globally. Certificates for regional services such as an ALB are provisioned in the service’s Region instead.
- Amazon Macie // Amazon Macie discovers and classifies sensitive data, such as personally identifiable information, in Amazon S3 and produces findings for investigation. It identifies exposure or sensitive-data risks rather than detecting general account and network threats.
- Amazon GuardDuty // GuardDuty continuously analyzes sources such as CloudTrail events, VPC Flow Logs, DNS logs, and S3 activity to detect suspicious behavior and generate findings, including anomalous EC2 activity such as connections to cryptocurrency-mining domains. It detects threats; Inspector assesses vulnerabilities and Macie discovers sensitive S3 data.
- Amazon Inspector // Amazon Inspector assesses supported compute resources and container images for software vulnerabilities and network exposure, such as vulnerabilities on EC2 instances. It is a vulnerability-management service, not the behavioral threat detector provided by GuardDuty.
- AWS Security Hub // Aggregate security findings and security-standard checks from services such as GuardDuty, Inspector, and Macie
- CloudTrail versus CloudWatch versus Config // CloudTrail records API activity, CloudWatch collects operational metrics and logs and supports alarms, and AWS Config records resource configuration history and evaluates compliance. Use Config to answer what a resource looked like at a prior time or to check a managed rule, such as imported ACM certificates nearing expiration.
- Load balancer Server Name Indication (SNI) // ALB and NLB listeners, and CloudFront, can use the hostname supplied in the TLS handshake to select a matching certificate; CLB supports only one certificate and not this feature.
- S3 SSE-S3 encryption // SSE-S3 encrypts each S3 object at rest using Amazon S3-managed keys and AES-256; it is enabled by default for new objects in buckets. It removes customer key-management work but does not provide the customer-managed KMS key-use audit trail of SSE-KMS.
- S3 DSSE-KMS encryption // DSSE-KMS applies two independent server-side encryption layers to an S3 object, one using a KMS key and one using an S3-managed key, for requirements that explicitly call for dual-layer encryption. It has higher request cost and latency than SSE-KMS and does not support S3 Bucket Keys.
- S3 SSE-C encryption // SSE-C has S3 perform server-side encryption using a customer-provided key that the customer retains outside AWS; the key must be supplied over HTTPS with each relevant request because S3 does not store it. It fits requirements to keep the key in an on-premises application while offloading encryption and storage to S3.
- S3 CORS configuration // An S3 CORS configuration returns browser response headers permitting cross-origin requests from specified origins, methods, and headers; a wildcard origin can permit requests from any origin. CORS controls browser behavior, not authorization, so bucket policies and IAM permissions must still grant access.
- Amazon S3 presigned URLs // A presigned URL grants temporary access to a specific S3 operation, commonly GET or PUT, using the permissions of the principal that signed it. The URL stops working at its expiration or when the signer’s credentials expire or lose permission, whichever comes first.
- Amazon S3 Access Points // S3 Access Points provide separate endpoints and policies for applications or groups accessing a shared bucket, allowing each policy to restrict a service to its own prefix. A VPC-origin access point requires an appropriate VPC endpoint, and the endpoint policy and S3 policies must permit the requested access.
- AWS IAM Access Analyzer // IAM Access Analyzer evaluates resource-based policies and reports resources that allow access from outside an account or organization. It analyzes external access; Access Advisor instead reports service last-accessed information, while Inspector finds software vulnerabilities.
- S3 SSE-KMS encryption // SSE-KMS encrypts S3 objects using a KMS key, providing KMS key-policy control, key-use audit events, and optional automatic key rotation; the caller and S3 must be authorized to use the key. KMS requests occur during object operations and can affect request cost or quotas, while SSE-S3 lacks the same customer-managed key-use audit.
- S3 Versioning and MFA Delete // S3 Versioning preserves prior object versions so an accidentally deleted or overwritten object can be recovered; MFA Delete adds an MFA check for permanently deleting object versions and for suspending versioning. Enable both when the requirement is protection against accidental object deletion rather than an immutable retention period.
- CloudFront origins and field-level encryption // CloudFront cache behaviors can route path patterns to different origins, and an origin group can fail over from a primary origin to a secondary origin. Field-level encryption protects selected fields in POST requests using a public key, rather than encrypting every field or relying on KMS for that feature.
- Amazon EBS encryption // EBS encryption protects volume data at rest, data moving between the volume and supported EC2 instances, and snapshots created from the encrypted volume. Volumes restored from an encrypted snapshot remain encrypted, with AWS KMS managing the encryption keys.
- Client-side encryption // Client-side encryption encrypts data locally before sending it to S3, allowing a company to use its proprietary algorithm and retain control of the encryption keys on premises. S3 stores ciphertext and does not perform the application’s encryption or decryption.
- CloudFront and Aurora read scaling // CloudFront caches cacheable responses near viewers to absorb repeated web-content reads, while Aurora Replicas serve read-only database queries to scale database read capacity. Use both when read spikes affect the web delivery layer and the database; a replica does not replace CloudFront caching, or vice versa.

## Content Domain 2: Design Resilient Architectures

### Availability, backup, and disaster recovery — Task 2.2

- Recovery Time Objective (RTO) // RTO is the longest acceptable interval between a disruption and restored service. A preconfigured Aurora Global Database secondary with managed failover can meet a 15-minute recovery target.
- Recovery Point Objective (RPO) // RPO is the maximum tolerable age of recoverable data at failure, expressed as data loss in time. Aurora Global Database typically has subsecond cross-Region lag, meeting a five-minute RPO; for a shared POSIX file system, EFS Standard is multi-AZ and AWS Backup cross-Region recovery points scheduled every eight hours or less meet an eight-hour RPO.
- Backup and restore DR // Back up data and configuration, then rebuild or restore the workload only after an incident; this usually has the lowest ongoing cost but the longest RTO. Choose it when the business can tolerate the time needed to provision infrastructure and restore data.
- Pilot light DR // Keep essential data stores and other core components replicated and ready in the recovery environment, but leave most application resources off. Recovery is faster than backup-and-restore but requires provisioning and starting the remaining stack.
- Warm standby DR // Keep a scaled-down but fully functional copy of the workload running in the recovery environment and scale it up during failover. Because core services are already active, recovery is faster than pilot light, where only essential components remain running.
- Multi-site active-active DR // Run production workloads in multiple sites or Regions simultaneously and route traffic to healthy locations. This provides the lowest recovery time because capacity is already serving users, at the cost of operating and synchronizing multiple production environments.
- AWS Backup plans and vaults // AWS Backup plans define scheduled backup rules, retention, lifecycle transitions, and copy actions for supported resources; backup vaults store and organize recovery points and can enforce access controls. Use a plan to centrally apply consistent schedules rather than configuring each resource separately.
- AWS Backup service selection // Use AWS Backup when centralized policies, retention, and cross-Region or cross-account copies are needed across supported services; service-native backups may be simpler for an isolated workload. For a shared POSIX file system, EFS Standard provides multi-AZ availability, and AWS Backup scheduled cross-Region recovery points every eight hours or less satisfy an eight-hour RPO.
- Cross-account and cross-Region backup // Copy recovery points to another Region for regional recovery and, when needed, to a separately controlled account to reduce exposure to source-account compromise. For a shared POSIX file system, EFS Standard provides multi-AZ availability, and AWS Backup can schedule cross-Region copies at intervals of eight hours or less for an eight-hour RPO.
- AWS Backup policies with Organizations // Use AWS Backup policies with AWS Organizations to centrally define backup plans and assign them to selected organization accounts or organizational units. The policy can govern supported resources without separately configuring each account.
- S3 replication // S3 replication asynchronously copies new objects between versioned source and destination buckets; existing objects require S3 Batch Replication, while a one-time `aws s3 sync` can copy missing or changed objects. Replicating SSE-KMS objects requires enabling encrypted-object replication, permission to decrypt with the source key and encrypt with the selected destination key; even multi-Region KMS keys do not eliminate S3 decryption and re-encryption. For serverless SQL over protected S3 data, use SSE-KMS and CRR for regional copies and Athena to query the objects directly.
- RDS Multi-AZ deployment // A traditional RDS Multi-AZ DB instance synchronously replicates to a standby in another Availability Zone in the same Region for managed high availability and automatic failover, not read scaling; read replicas are asynchronous and can be same-AZ, cross-AZ, or cross-Region. For full-stack availability, also place web instances in multiple AZs behind an Elastic Load Balancer; SQL Server Multi-AZ uses Database Mirroring or Always On Availability Groups. An engine-version upgrade updates both nodes and can cause downtime, while operating-system maintenance can update the standby first, promote it, then update the former primary.
- Aurora Global Database // Aurora Global Database has one read/write primary Region and up to 10 read-only secondary Regions, with typical cross-Region replication lag under one second; it is for regional reads and disaster recovery, not multi-writer writes. A secondary can be promoted during a regional outage, with recovery commonly around a one-second RPO and under-one-minute RTO; a preconfigured secondary can therefore meet a five-minute RPO and 15-minute RTO. Replication is cluster-wide, not limited to selected tables, so keep globally shared data in its own cluster and regional-only data in separate regional Aurora clusters.
- DynamoDB point-in-time recovery (PITR) // Enable DynamoDB PITR to restore a table to a chosen second within its continuous-backup retention window (up to 35 days), such as the moment just before corrupt data was written. Restore creates a new table, allowing recovery without overwriting the source.
- DynamoDB deletion protection // Enable deletion protection to prevent a DynamoDB table from being deleted until protection is disabled. It prevents accidental deletion but does not preserve prior item versions; enable PITR or backups separately for data recovery.
- DynamoDB global tables // DynamoDB global tables replicate a table across Regions so each regional replica can serve local reads and writes, with automatic replication typically converging in under a second; provisioned capacity with auto scaling adjusts throughput to demand. The default multi-Region consistency mode is eventual, so workloads requiring strong multi-Region consistency must use a supported strong-consistency configuration.
- AWS Step Functions // AWS Step Functions coordinates multi-step workflows using state types such as Task, Choice, Parallel, Wait, and retry or error handling. Use it when services need durable orchestration and explicit control flow instead of custom coordination code.
- Step Functions Standard versus Express // Standard workflows suit long-running, durable, auditable executions and can run for up to one year; Express workflows suit high-volume, short-duration processing and run for at most five minutes. Choose Standard when execution history and long-running orchestration matter, and Express for brief event-processing workloads.
- ElastiCache Multi-AZ failover // For a Redis or Valkey replication group, enable Multi-AZ and automatic failover so a replica can be promoted when the primary fails, reducing cache downtime and potential data loss. Read replicas alone add read capacity and do not provide the same automatic failover guarantee.
- Availability Zone capacity planning // Distribute baseline application capacity across at least two Availability Zones so the surviving AZ can continue the required service after one AZ fails; use an Auto Scaling group and load balancer to replace or route around unhealthy instances. For a workload needing two instances after an AZ loss, four minimum instances split two per AZ and a maximum of six supports peak growth.
- Multi-AZ minimum capacity // Set the Auto Scaling group minimum high enough that losing one AZ still leaves the workload’s required baseline; for two required instances across two AZs, keep four minimum instances, two per AZ. Set maximum capacity separately for peaks (six in that example); desired capacity defaults to minimum when not specified.
- EBS snapshots // EBS snapshots are point-in-time, incremental backups that are independent of Availability Zones; create a volume from a snapshot in any AZ, or copy the snapshot to another Region for regional recovery. The snapshot archive tier lowers storage cost but retrieval typically takes 24–72 hours, so use it only when that restore delay is acceptable.
- EC2 Capacity Reservations // A Capacity Reservation reserves matching On-Demand EC2 capacity in a specified Availability Zone for as long as the reservation remains active; instance type, platform, and other attributes must match. It is billed at On-Demand rates even when unused, though applicable Reserved Instance or Savings Plan discounts can reduce the bill.
- Elastic Network Interfaces (ENI) // An ENI is an AZ-bound virtual network interface with private IPv4 addresses, a MAC address, and associated security groups; it can have primary and secondary addresses. Detach and attach it to another instance in the same AZ to move its network identity during failover.
- RDS Multi-AZ standby // A traditional RDS Multi-AZ standby synchronously receives database changes in another AZ and is not a read endpoint. On failover, RDS updates the DB endpoint’s DNS CNAME to the standby, so the application continues using the same endpoint without manual endpoint changes.
- RDS and Aurora automated backups and snapshots // RDS automated backups retain 1–35 days (setting retention to zero disables them) and support point-in-time restore to a new DB instance; Aurora automated backups retain 1–35 days and cannot be disabled. Manual snapshots are user-initiated and persist until deleted; restoring an RDS snapshot or Aurora recovery point creates a new database. To share an encrypted RDS snapshot with another account, share the snapshot and authorize that account to use its KMS key; cross-Region automated backup copies support regional recovery.
- Route 53 health checks for private endpoints // Route 53 health checkers are outside the VPC and cannot directly reach private endpoints. Publish application health as a CloudWatch metric and configure a CloudWatch-alarm health check for DNS failover decisions.
- S3 replication (CRR/SRR) // Cross-Region Replication (CRR) and Same-Region Replication (SRR) asynchronously copy new objects between versioned buckets in different or the same Region; existing objects need S3 Batch Replication. Configure replication permissions and destination encryption as required; a delete marker can replicate when configured, but a permanent deletion of a specific object version is not replicated.
- Secrets Manager multi-Region secrets // Replicate a Secrets Manager secret to selected Regions to keep regional read replicas synchronized with the primary secret. Promote a replica to a standalone secret when the primary Region is unavailable and independent management is needed.
- AWS Elastic Disaster Recovery (DRS) // AWS DRS continuously replicates source-server block data to low-cost staging resources in AWS, then launches recovery EC2 instances and EBS volumes during a drill or failover. It reduces recovery time without keeping a full production fleet running and supports failback to the source environment.
- Amazon RDS storage autoscaling // RDS storage autoscaling increases allocated storage up to a configured maximum when free space remains below 10% for at least five minutes and at least six hours have passed since the previous storage modification. It reduces manual intervention for unpredictable growth but does not shrink storage or exceed the configured maximum.
- Amazon RDS Custom for Oracle // RDS Custom for Oracle provides managed database operations while allowing DBAs to access and customize the database environment and host operating system, which standard RDS does not permit. Use its Multi-AZ configuration when that customization is required together with managed standby failover.
- Prebuilt AMI recovery // Create an AMI after installing and configuring the application stack, then copy the image to each recovery Region because AMIs are Region-specific. Launching from a prepared regional image avoids repeating lengthy software installation during recovery and supports a short RTO.
- Amazon RDS cross-Region disaster recovery // For regional database recovery, copy RDS automated backups across Regions or maintain a cross-Region read replica; the asynchronous replica can be promoted to a standalone database after a regional failure. Multi-AZ alone protects within one Region, while read replicas also serve read scaling and may lag behind the source.
- Multi-tier application high availability and scaling // Place EC2 web instances in an Auto Scaling group spanning multiple AZs and register them with an Application Load Balancer target group so traffic reaches healthy instances and capacity can scale. Pair the web tier with RDS Multi-AZ for database failover, or Aurora reader instances in separate AZs when read scaling is also required.

## Content Domain 3: Design High-Performing Architectures

### Elastic compute and storage — Tasks 3.1–3.2

- EC2 instance family selection // Choose compute-optimized families for CPU-bound work, memory-optimized for memory-heavy databases or analytics, storage-optimized for high local I/O, and accelerated-computing families for GPU or specialized processing; select by the workload bottleneck.
- EC2 purchasing options // Use On-Demand for flexible short-term capacity, Reserved Instances or Savings Plans for committed baseline use, and Spot for interruption-tolerant work or variable peaks. Mixed Auto Scaling capacity can pair a reserved baseline with Spot and fallback capacity; Dedicated Hosts provide host-level placement and support server-bound licenses, while Dedicated Instances provide dedicated tenancy without host control.
- EC2 placement groups // A cluster placement group packs instances within one AZ for low-latency, high-throughput communication such as HPC; spread placement isolates a small number of critical instances across hardware (up to seven per AZ), while partition placement separates distributed fleets across racks and can span AZs.
- EC2 Auto Scaling policy selection // Target tracking adjusts capacity to maintain a chosen metric target, such as average CPU near 50% or SQS backlog per in-service worker; step scaling responds to alarm breaches, and scheduled scaling handles known time-based demand. For queue workers, normalize visible backlog by running capacity when raw queue depth does not represent per-worker load.
- EC2 Auto Scaling health checks // An Auto Scaling group can use EC2 or load-balancer health checks to identify and replace unhealthy instances, with a grace period to avoid premature replacement during startup. Health replacement terminates the unhealthy instance before launching a replacement, whereas AZ rebalancing launches before terminating to preserve capacity.
- Application Load Balancer versus Network Load Balancer // An ALB routes HTTP and HTTPS at Layer 7 using host, path, or other request attributes; an NLB handles Layer 4 TCP, TLS, and UDP, supports static addresses, and sends instance-target traffic to the primary private IP on the primary network interface. Use NLB rather than ALB for UDP; Global Accelerator can route TCP/UDP clients to healthy regional load balancers using static anycast IPs.
- ECS, EKS, and Fargate // ECS and EKS orchestrate containers, and both can run supported tasks on Fargate without managing worker instances; ECS on EC2 incurs the underlying EC2 and EBS charges, while Fargate pricing is based on requested task vCPU and memory. API Gateway and Lambda can receive and validate API requests before dispatching longer backend jobs to ECS on Fargate, which can run beyond Lambda’s 15-minute limit and mount EFS for persistent shared files; EventBridge Scheduler can start scheduled ECS tasks, and Kinesis Data Streams can buffer real-time input.
- AWS Batch // AWS Batch queues, schedules, and provisions compute for batch jobs, scaling suitable EC2 or Fargate capacity to queued work; Step Functions can orchestrate job stages and S3 can hold durable inputs or outputs.
- EFS mount targets // EFS clients connect through mount targets in a VPC; create one in each AZ where clients run and have instances use the local-AZ target to reduce cross-AZ latency and transfer charges while retaining shared access.
- EFS throughput modes // Bursting throughput scales with file-system size and accumulates credits for spikes; for sporadic peaks with low average throughput, use bursting with General Purpose performance mode and EFS Standard storage (bursting is the default for file systems under 1 TiB). Provisioned throughput sets capacity independently of stored data, useful when a small file system needs consistently high throughput; elastic throughput scales automatically with demand.
- S3 multipart upload // Multipart upload sends one object as independently retryable parts, often in parallel, and is recommended for objects above 100 MB and required above 5 GB. Combine it with Transfer Acceleration for distant large-file uploads when the added acceleration charge is justified.
- S3 byte-range GET // An S3 GET with an HTTP Range header returns only the requested byte interval, allowing partial reads or parallel retrieval; use it to inspect a small prefix of large objects without downloading the full object.
- S3 Transfer Acceleration // Transfer Acceleration routes long-distance uploads or downloads through nearby CloudFront edge locations and the AWS network; it can be combined with multipart upload for large files, while CloudFront with an S3 origin can serve downloads and support upload requests. Acceleration fees apply only to transfers that are accelerated, and internet uploads into S3 have no inbound data-transfer charge.
- Amazon CloudFront caching // CloudFront caches HTTP(S) content near viewers to reduce origin requests and latency, including content from custom on-premises origins; with S3 as origin it can serve downloads and support upload requests. A distribution can route request types to different origins, use primary and secondary origins for failover, and apply field-level encryption to selected POST fields; geo restriction can block viewers by country.
- Amazon S3 and CloudFront static delivery // Store static assets in S3 and distribute them through CloudFront for edge caching, lower origin load, and global delivery; a Route 53 alias can map a custom domain to the distribution, while CloudFront can front dynamic API Gateway/Lambda-backed endpoints using DynamoDB. S3-to-CloudFront transfer is not charged as internet egress, and CloudFront can lower delivery costs compared with serving every viewer request directly from S3.
- AWS Outposts and Wavelength // Outposts brings AWS infrastructure and services into a customer facility for local processing and data residency; EKS Anywhere on Outposts can run Kubernetes workloads on premises while integrating with AWS APIs. Wavelength Zones place eligible AWS services in 5G carrier networks for low-latency mobile applications.
- EBS Multi-Attach // A supported io1 or io2 EBS volume can attach read/write to as many as 16 Nitro instances in the same AZ; the application must coordinate concurrent writes and use a cluster-aware file system because EBS does not provide shared-file locking.
- EFS performance modes // Select General Purpose at file-system creation for latency-sensitive workloads; Max I/O supports higher aggregate throughput and operations per second for highly parallel work such as big-data analysis, at the cost of higher metadata-operation latency.
- Auto Scaling cooldown // A cooldown after a scaling activity gives metrics time to stabilize before another scaling action; the default cooldown for a simple scaling policy is 300 seconds, while target tracking and step policies use their own scaling behavior.
- S3 Express One Zone // S3 Express One Zone is high-performance object storage in a single-AZ directory bucket, designed for very high request rates and consistent single-digit-millisecond latency; placing compute in the same AZ can reduce latency, but the data does not have multi-AZ storage resilience.
- Elastic Beanstalk // Elastic Beanstalk deploys and operates an application environment by provisioning resources such as EC2, Auto Scaling, and load balancers while the developer supplies application code. The service itself has no additional charge, but provisioned AWS resources are billed.
- Amazon ECR // Amazon ECR stores and manages container images in private or public repositories; IAM controls access, and image scanning, tags, and lifecycle policies support image security and cleanup.
- CloudWatch Unified Agent // The CloudWatch agent runs on EC2 or on-premises servers to publish logs and guest OS metrics such as memory, disk, network, and process data, which basic EC2 metrics do not provide; Systems Manager Parameter Store can centrally hold its configuration.
- EC2 hibernation // Hibernation suspends the OS to disk, saving RAM and process state to an encrypted EBS root volume; on restart memory and running processes are restored, avoiding application bootstrap. It requires a supported non-bare-metal instance and configuration, RAM no greater than 150 GiB, and a hibernation period of no more than 60 days.
- Auto Scaling AZ rebalancing // When an Auto Scaling group becomes uneven across enabled AZs, it rebalances by launching replacement capacity before terminating instances in overrepresented zones, so capacity is not reduced during the rebalancing sequence; this differs from replacing an unhealthy instance.
- Auto Scaling on SQS backlog // Scale a worker Auto Scaling group from SQS backlog, preferably using visible messages divided by the number of InService workers as backlog per instance and targeting an acceptable value. This ties worker capacity to queue demand more directly than scheduled scaling or CPU alone.
- EBS Fast Snapshot Restore // Fast Snapshot Restore fully initializes volumes created from an enabled snapshot so they deliver provisioned performance immediately instead of incurring first-read lazy-loading latency; it is enabled per snapshot and AZ and adds cost.
- S3 per-prefix request performance // S3 scales request performance across key prefixes; each prefix supports at least 3,500 write-class requests or 5,500 GET/HEAD requests per second. Distribute high-volume keys across prefixes, such as customer-specific prefixes in one bucket, rather than creating a bucket for each workload.
- Amazon FSx for Lustre // FSx for Lustre is a high-performance parallel file system for HPC and data-processing workloads, with integration to S3 for large data sets. Scratch file systems provide temporary, unreplicated burst performance, while persistent file systems replicate data within one AZ and replace failed files.
- AMI copying across Regions // Copying an AMI to another Region creates a regional AMI and its backing EBS snapshot there; launching an instance from that copy adds the instance in the destination Region. AMIs and snapshots are regional resources, so copying the AMI does not move the original instance.
- Shared storage for EC2 fleets // Data written to an instance’s EBS volume is local to that instance, so load-balanced servers need shared storage to see one another’s uploads. Migrate files to EFS for a shared NFS file system or S3 for durable object storage, then update the application to use that shared store.
- CloudFront origins, failover, and field-level encryption // A CloudFront distribution can route request types to separate origins, configure a primary and secondary origin group for failover when the primary fails, and encrypt selected sensitive fields in POST requests at the edge using field-level encryption. These are distinct from geographic viewer restrictions.
- EKS Cluster Autoscaler // The Kubernetes Cluster Autoscaler detects pods that cannot be scheduled because worker-node capacity is insufficient and adjusts the EKS node group’s EC2 Auto Scaling group to add or remove nodes. It complements the Horizontal Pod Autoscaler, which changes pod count but does not itself increase worker-node capacity.
- AWS Transfer Family with EFS // AWS Transfer Family provides a managed SFTP endpoint that can use encrypted EFS as shared file storage; a VPC-hosted endpoint can use Elastic IPs and security groups to restrict source networks, while POSIX identity mappings and IAM policies control user access. This replaces self-managed SFTP servers and local user provisioning.

### Scalable network architectures — Task 3.4

- AWS Site-to-Site VPN versus Direct Connect // Site-to-Site VPN uses IPsec tunnels between a customer gateway representing the on-premises router and a virtual private gateway on the AWS side, encrypting traffic over the public internet; security groups, network ACLs, and routes further restrict permitted flows. Direct Connect provides a dedicated, consistent private path with greater throughput but is not encrypted by default, so pair it with VPN when encryption is required or use VPN as a rapid encrypted backup; DataSync can transfer NFS data to EFS through an interface endpoint over a private Direct Connect VIF on a scheduled task.
- AWS Transit Gateway versus VPC peering // Transit Gateway is a managed hub for transitive routing among many VPCs and on-premises networks, supports ECMP across multiple dynamically routed VPN tunnels to increase throughput beyond the 1.25-Gbps-per-tunnel limit, and reduces hub-and-spoke connection overhead. VPC peering provides direct, non-transitive connectivity between two VPCs; inter-Region peering can provide a network path to a regional EFS mount target when routing, DNS, and security rules are configured.
- VPC endpoint selection // Gateway endpoints provide private S3 or DynamoDB access through route-table entries and have no endpoint hourly charge; interface endpoints use PrivateLink ENIs and security groups for services such as SQS or EFS and can be reached from on-premises over Direct Connect. DataSync can send on-premises NFS data directly to EFS through an interface endpoint over a private Direct Connect VIF, including on a scheduled task; endpoint and data-processing charges may apply.
- Route 53 failover routing // Configure primary and secondary records with health checks for active-passive DNS failover; when the primary is unhealthy, Route 53 answers with the healthy secondary, such as an S3-hosted static error page. A predeployed AWS application behind an ALB can serve as failover, and Storage Gateway stored volumes can asynchronously back up on-premises data to S3.
- Route 53 latency routing // Latency-based routing answers DNS queries with the Region offering the lowest measured latency to the user; deploy web endpoints in multiple Regions and use regional database read replicas when low-latency reads are also required. It optimizes measured latency, unlike geolocation routing, which selects by query location.
- Gateway Load Balancer (GWLB) // GWLB transparently distributes traffic to and from virtual network appliances such as firewalls; it operates at Layer 3 and encapsulates appliance traffic with GENEVE on port 6081, combining appliance insertion with scaling.
- Elastic Load Balancer stickiness // Stickiness keeps a client associated with the same target across requests, aiding session continuity but potentially skewing load. ALB and Classic Load Balancer support cookie-based affinity; NLB stickiness is based on source IP, not cookies.
- Route 53 alias records // An alias record can point a DNS name, including a zone apex, to supported AWS resources or another record in the same hosted zone; unlike a CNAME, it works at the apex. Alias answers follow changing target addresses and have no user-configurable TTL; aliases to supported AWS resources avoid Route 53 query charges.
- Route 53 geolocation routing // Geolocation routing selects DNS answers from the location of the DNS query (continent, country, or US state), not measured latency; use a default record for unmatched locations and health checks where needed. It can direct or restrict service by geography, while CloudFront geo restriction directly blocks viewers outside allowed countries.
- Route 53 weighted routing // Weighted routing distributes DNS responses among records in proportion to relative weights, which need not total 100, for traffic splitting or version tests; weight zero suppresses a record unless all records have zero weight, when they are returned equally.
- API Gateway endpoint types // Edge-optimized API endpoints use CloudFront to serve global clients while the API remains in one Region; regional endpoints serve clients in or near a Region, and private endpoints are reachable from a VPC through an interface endpoint.
- CloudFront Functions vs. Lambda@Edge // CloudFront Functions run lightweight JavaScript for sub-millisecond viewer-request or viewer-response changes; Lambda@Edge supports Node.js or Python at viewer or origin events and suits longer execution or network, filesystem, and request-body access.
- VPC subnet usable IPv4 capacity // AWS reserves the first four and last IPv4 addresses of every subnet, leaving five fewer usable addresses than the CIDR total; size the subnet based on remaining capacity.
- Regional NAT Gateway // A Regional NAT Gateway is a VPC-associated managed NAT service that can serve private workloads across AZs and expand as AZs are used, avoiding the need to create and route each AZ through its own public subnet and NAT gateway.
- Egress-only Internet Gateway // An egress-only Internet Gateway provides IPv6-only outbound internet connectivity for VPC instances while blocking internet-initiated inbound connections; route ::/0 through it for this behavior.
- AWS VPN CloudHub // VPN CloudHub provides low-cost hub-and-spoke communication among multiple remote sites using Site-to-Site VPN connections to one virtual private gateway; sites can communicate with each other and with a Direct Connect-connected site, using dynamic routing over internet-based VPN links.
- NAT instance capabilities // A customer-managed EC2 NAT instance can perform port forwarding, have security groups, and serve as a bastion host; unlike a managed NAT Gateway, the customer manages its availability, scaling, and maintenance.
- Availability Zone IDs // AZ IDs identify the same physical Availability Zone consistently across AWS accounts, whereas AZ names such as us-west-2a can map to different physical zones in different accounts; use IDs when cross-account placement must match.
- Route 53 geoproximity routing // Geoproximity routing sends DNS traffic based on geographic locations of users and resources; a positive or negative bias expands or shrinks the geographic area that sends traffic to a resource, unlike geolocation routing’s fixed location matching.
- Geographic content access controls // CloudFront geo restriction blocks viewers from selected countries at the content-delivery layer; Route 53 geolocation routing instead selects DNS answers based on the location of a DNS query and can direct or restrict routing by location. Use the CloudFront restriction to enforce viewer access and DNS geolocation when selecting regional endpoints.
- Route 53 CNAME records // A CNAME maps a DNS subdomain to another domain name, such as an application hostname to a provider hostname; DNS does not allow a CNAME at the hosted-zone apex. Use a Route 53 alias rather than a CNAME when the root domain must point to a supported AWS resource or same-zone record.
- DNS TTL caching // DNS resolvers cache a record answer for its TTL, so changing a Route 53 record does not immediately redirect every client; users may continue reaching the previous load balancer until cached answers expire. Lowering TTL in advance can shorten planned cutover time, but does not invalidate existing cached responses.

### Database and data-ingestion performance — Tasks 3.3 and 3.5
- RDS read replicas // Amazon RDS read replicas use engine-native asynchronous replication to offload read queries; applications must route reads to a replica endpoint, and replicas can lag behind the source. They can be created across Availability Zones or Regions and promoted for disaster recovery; replication within one Region has no data-transfer charge, while cross-Region replication does. Replica limits depend on the engine, with some configurations supporting up to 15, and RDS automated backups can also be copied across Regions for recovery.

- Amazon Kinesis Data Streams // Kinesis Data Streams durably ingests and decouples real-time producers from multiple independent consumers such as AWS Lambda; Lambda can filter or redact records, write processed results to DynamoDB, and other applications can independently consume the original records. It preserves order within a shard and supports retries and replay during the retention window, which defaults to 24 hours and can be extended to 365 days. On-demand capacity fits unpredictable spikes without manual shard provisioning.
- Kinesis on-demand capacity // On-demand capacity automatically adjusts a Kinesis Data Stream to changing traffic without manually provisioning shards, making it a good fit for unpredictable spikes. Provisioned capacity is generally preferable when throughput is steady and predictable.
- Kinesis enhanced fan-out // Enhanced fan-out gives each registered Kinesis Data Streams consumer a dedicated 2 MB/s read pipe per shard, avoiding the shared read-throughput bottleneck when consumers process the same stream concurrently.
- Kinesis producer batching // Batching Kinesis records into fewer producer requests reduces per-request overhead and uses shard write throughput more efficiently, helping relieve throttling without adding shards. Batching does not increase a shard’s underlying throughput limits.
- Amazon Data Firehose // Amazon Data Firehose buffers streaming records, can optionally transform them with Lambda, and delivers them to supported destinations such as S3 without requiring you to manage shards or consumers. It is a managed delivery path, not a substitute for Kinesis Data Streams when multiple applications need independent stream consumption or replay.
- Kinesis Data Analytics // Kinesis Data Analytics, now Amazon Managed Service for Apache Flink, runs managed Flink applications for real-time stream transformations and analytics, commonly reading from Kinesis Data Streams or Amazon MSK. In a streaming pipeline, Data Streams ingests events, the analytics application processes them, and Firehose can deliver results to S3.
- AWS DMS S3-to-Kinesis integration // For supported S3 source configurations, AWS Database Migration Service can load S3 data into Kinesis Data Streams and capture supported ongoing changes, providing a managed bridge instead of custom streaming code. Check source-format and change-capture support for the specific S3 workflow.
- Amazon DataSync // AWS DataSync automates, accelerates, schedules, and monitors online file transfers to AWS storage such as S3, EFS, and FSx, with integrity verification and metadata preservation. Transfers involving on-premises storage require a DataSync agent; supported AWS-to-AWS transfers can be agentless, and DataSync can migrate files before another service such as File Gateway serves ongoing access.
- DataSync to EFS over Direct Connect // For recurring on-premises NFS-to-EFS transfers, deploy a DataSync agent with access to the source and use private connectivity through Direct Connect and a DataSync interface VPC endpoint. This transfers files directly to EFS without staging them through S3 or an internet-facing path.
- AWS Transfer Family // AWS Transfer Family provides managed SFTP, FTPS, and FTP endpoints backed by Amazon S3 or EFS, so partners can keep using standard file-transfer clients without you operating SFTP servers. A private endpoint can span multiple AZs; users can be mapped to IAM roles and POSIX identities, and managed workflows can invoke Lambda after uploads complete.
- AWS Database Migration Service (DMS) // AWS DMS migrates database data while the source remains available, using an initial load and, when needed, change data capture to replicate ongoing changes. Provisioned replication instances can use Multi-AZ standby for resilience, while DMS Serverless automatically provisions and scales capacity for variable workloads; DMS moves data, whereas SCT converts heterogeneous schemas.
- AWS Application Migration Service (MGN) // AWS Application Migration Service rehosts supported physical, virtual, or cloud servers by installing its Replication Agent and continuously replicating source disks at the block level. Launch test instances to validate the migration, then perform cutover after replication is current; it is a lift-and-shift path rather than application refactoring.
- AWS Schema Conversion Tool (SCT) // AWS SCT assesses and converts database schemas and code objects when source and target engines differ, such as SQL Server to PostgreSQL; AWS DMS then migrates the data. A same-engine migration such as Oracle to Oracle generally needs no schema conversion, though SCT can identify compatibility issues.
- Six migration strategies (6 Rs) // The six common migration strategies are rehost (move as-is), replatform (make limited optimizations), repurchase (replace with a product), refactor or re-architect (redesign), retain (keep for now), and retire (decommission). Choose among them according to modernization goals, constraints, and the effort the workload can tolerate.
- AWS Glue and Data Catalog // AWS Glue provides managed, serverless ETL jobs, while its Data Catalog stores table metadata for services such as Athena and Redshift. A crawler can infer schemas from S3 files for ad hoc Athena queries, and Glue jobs can transform or clean S3 data before loading a warehouse.
- AWS Lake Formation // AWS Lake Formation helps build and govern a data lake by centrally applying fine-grained permissions to cataloged databases, tables, columns, and underlying data. It does not perform ETL or archive objects: use AWS Glue for transformations and S3 Lifecycle rules for transitions such as moving raw data to Glacier Deep Archive.
- Amazon EMR // Amazon EMR is a managed environment for distributed big-data frameworks such as Spark and Hadoop, so choose it when the need is cluster-based data processing. When the requirement is a high-performance parallel file system for HPC or machine learning data, Amazon FSx for Lustre is the storage service rather than EMR.
- Amazon Redshift and Spectrum // Amazon Redshift is a massively parallel, columnar data warehouse for SQL analytics and joins; Redshift Spectrum queries S3 data without loading it but still uses Redshift compute. Redshift Serverless provides a serverless warehouse option, and Redshift ML lets analysts create and use models with SQL through SageMaker integration.
- Amazon OpenSearch Service // Amazon OpenSearch Service indexes events for low-latency full-text search, partial matches, and interactive search analytics across fields, unlike a database lookup limited to keys or defined indexes. Stream data can be delivered for indexing, and the resulting search experience can be visualized in Amazon Quick.
- Amazon Quick // Amazon Quick (called QuickSight in older materials) is managed business intelligence for building interactive dashboards and visualizations from supported data sources, including indexed search data. It presents and explores data; it does not ingest streams or provide OpenSearch-style full-text indexing.
- Amazon Comprehend custom entity recognition // Amazon Comprehend custom entity recognition is a managed NLP feature for finding domain-specific entity types, such as ingredient names, in unstructured text. You provide labeled examples to train the recognizer, while Comprehend manages model infrastructure and inference; for example, an S3 upload event can invoke Lambda to extract entities and write lookup results to DynamoDB.
- Database read scaling and caching // Use relational read replicas to route read-only queries away from a writer, ElastiCache for frequently accessed or compute-intensive results, and DynamoDB Accelerator (DAX) for an in-memory cache in front of DynamoDB. CloudFront can absorb spikes in cacheable web content, while database replicas handle database reads; each requires routing or cache integration appropriate to the workload.
- ElastiCache Redis vs. Memcached // ElastiCache for Redis supports persistence, sorted sets, replication, and Multi-AZ automatic failover, making it suitable for durable in-memory use cases such as leaderboards. Memcached is a simpler, multithreaded, nonpersistent cache that can shard data across nodes but does not provide replication-based high availability.
- Amazon RDS Proxy // Amazon RDS Proxy pools and reuses database connections so bursts of short-lived clients such as Lambda functions are less likely to exhaust database connections; the proxy is accessed privately, so clients must reach it within the VPC. It smooths connection pressure but does not queue application work, so use SQS when requests should be buffered and processed asynchronously.
- Aurora Replicas // Aurora Replicas share the cluster’s storage volume with the writer, providing read-only capacity with typically very low replication lag, often measured in tens of milliseconds; up to 15 can be attached to a cluster. Applications can use the reader endpoint to distribute reads, and replicas can be promoted automatically for writer failover or scaled with Aurora Auto Scaling.
- Amazon Redshift Serverless // Amazon Redshift Serverless runs a massively parallel Redshift data warehouse without requiring a fixed provisioned cluster, while scaling compute to workload demand. It supports SQL analytics and Redshift ML, which lets analysts create and use models through SQL without building custom Python model code.
- Aurora I/O-Optimized // Aurora I/O-Optimized removes per-I/O charges in favor of a higher storage price, making total cost more predictable for workloads with frequent or spiky reads and writes. Choose it when I/O costs or performance are a concern; it does not require manually provisioning IOPS.
- DynamoDB on-demand capacity mode // DynamoDB on-demand charges per read and write request and automatically accommodates variable workloads without capacity planning, so it fits unknown or rapidly changing traffic. Provisioned capacity with auto scaling is generally more economical for steady, predictable workloads, while on-demand often costs more at sustained high usage.
- AWS Glue DataBrew // AWS Glue DataBrew is a visual, no-code service for profiling and preparing data, including Parquet files in S3, with reusable recipes for cleaning and transforming datasets. Recipes record, share, and audit preparation steps, while profiling surfaces statistics, nulls, and data types.
- Amazon Comprehend // Amazon Comprehend provides managed, pre-trained NLP for tasks such as sentiment analysis, entity detection, and topic classification on text without requiring you to train a custom model. Use it after extracting text from documents when standard sentiment or entity detection is sufficient; custom entity recognition is for domain-specific labels.

## Content Domain 4: Design Cost-Optimized Architectures

### Cost-aware storage, compute, and network choices — Tasks 4.1–4.4

- S3 Intelligent-Tiering // S3 Intelligent-Tiering automatically moves objects among access tiers as access patterns change, making it useful when usage is unpredictable; it charges a small per-object monitoring fee and has no retrieval fees. Its frequent-access tier applies initially, objects move to Infrequent Access after 30 days without access and to Archive Instant Access after 90 days, while optional archive tiers require restore before access. Lifecycle transitions cannot move objects back to S3 Standard; Intelligent-Tiering cannot transition to Standard-IA, and One Zone-IA cannot transition to Standard-IA or Intelligent-Tiering.
- EBS General Purpose SSD versus Provisioned IOPS SSD // General Purpose SSD (gp2 or gp3) is the cost-effective default for most workloads; gp2 can burst to 3,000 IOPS for occasional demand. Provisioned IOPS SSD (io1 or io2) costs more but is designed for sustained, predictable high IOPS; io1 or io2 is required for EBS Multi-Attach, which attaches a volume to multiple instances in the same AZ.
- EC2 Savings Plans versus Reserved Instances // Compute Savings Plans discount eligible EC2, Fargate, and Lambda usage with broad flexibility across instance families, sizes, operating systems, tenancy, and Regions, while EC2 Reserved Instances discount defined EC2 usage under a term commitment. Cover predictable baseline capacity with a commitment, then use Spot for interruptible variable work or On-Demand for capacity that cannot be interrupted.
- Spot Instances // EC2 Spot Instances use spare capacity at discounts of up to 90 percent but can be interrupted with a two-minute notice, so workloads must tolerate interruption and checkpoint or retry. A persistent Spot request reopens after interruption, canceling a request does not terminate an already running instance, and a Spot Fleet can replace interrupted capacity and optionally mix in On-Demand instances.
- AWS Cost Explorer // AWS Cost Explorer visualizes historical spending and forecasts future costs, and provides recommendations for purchasing Savings Plans or Reserved Instances. It helps analyze and plan costs but does not enforce spending limits or alert on unusual patterns by itself.
- AWS Budgets // AWS Budgets tracks cost, usage, or commitment metrics against actual or forecasted thresholds and can notify stakeholders when a budget is exceeded or coverage falls below a target. A Budgets action can also enforce a configured response, such as applying a policy, rather than only reporting the threshold.
- AWS Cost and Usage Report // The AWS Cost and Usage Report provides detailed line-item billing and usage data, typically delivered to S3 for granular analysis with tools such as Athena. Use it when detailed exports are needed rather than a dashboard or threshold alert.
- Cost allocation tags // Consistent resource tags such as project, team, or environment can be activated as cost allocation tags so billing tools attribute eligible costs to those dimensions. Tags do not automatically appear in cost reports until activated and may not apply to every charge.
- AWS Compute Optimizer // AWS Compute Optimizer analyzes utilization and configuration metrics to recommend suitable instance types and sizes for supported resources, helping right-size EC2. It provides recommendations rather than changing resources or selecting purchase commitments automatically.
- VPC endpoint and NAT cost tradeoff // An S3 or DynamoDB gateway VPC endpoint routes same-Region service traffic privately through route tables with no hourly or data-processing charge, avoiding NAT Gateway processing costs. Interface endpoints have hourly and per-GB charges, so compare those with NAT costs for other private service traffic at expected volume.
- AWS Organizations consolidated billing // Consolidated billing combines member accounts into one AWS Organizations bill and can aggregate usage for eligible volume pricing. Savings Plans and Reserved Instance benefits may be shared across accounts when benefit sharing is enabled and usage is eligible.
- EC2 and Auto Scaling right-sizing // Use measured demand and failure requirements to size instances and Auto Scaling capacity, distribute instances across Availability Zones, and reserve only the stable baseline. For example, two instances in each of three AZs leave four after one AZ fails; a minimum of two instances spread across AZs can provide a lower-cost baseline, with Reserved Instances suited to steady usage.
- EFS storage classes // EFS Standard and One Zone provide multi-AZ and single-AZ storage respectively; One Zone costs less but has less availability and durability, and automatic backups are enabled by default for One Zone file systems. Lifecycle management moves cold files to Infrequent Access or Archive for lower storage cost, with retrieval charges and delays that make Archive suitable only for rarely accessed data.
- S3 Requester Pays // Requester Pays makes authenticated requesters pay for their S3 requests and data downloads, while the bucket owner still pays storage charges. Requests must identify the requester as accepting the charge, and anonymous access is not supported.
- AWS Storage Gateway stored volumes // Stored volumes present iSCSI block storage to on-premises applications while keeping the full primary dataset on premises; scheduled backups are stored in AWS as EBS snapshots. Choose this when local access and on-site data residency are required, not when primary data should live in S3.
- AWS Storage Gateway Tape Gateway // Tape Gateway presents a virtual tape library over iSCSI to existing backup software, storing virtual tapes in S3 and archived tapes in S3 Glacier Flexible Retrieval. It lets organizations retain tape-based backup workflows without managing physical tape libraries.
- DynamoDB time to live (TTL) // DynamoDB TTL automatically deletes items after a per-item Unix epoch expiry timestamp, which is useful for expiring sessions or temporary records. Deletion is asynchronous and may occur days after the timestamp, so TTL is not an exact-time deletion or access-control mechanism.
- S3 Standard // S3 Standard is multi-AZ object storage for frequently accessed data and has no retrieval fee or minimum storage duration. It is cost-effective for short-lived, repeatedly read objects such as query results kept for only a day.
- S3 One Zone-IA // S3 One Zone-IA stores infrequently accessed data in one Availability Zone at lower storage cost than multi-AZ Standard-IA, but is suited only to noncritical or recreatable data. It has retrieval charges and a 30-day minimum storage duration, and lifecycle rules cannot transition it to Standard-IA or Intelligent-Tiering.
- AWS Storage Gateway cached volumes // Cached volumes present iSCSI block storage to on-premises applications, keep frequently accessed data in a local cache, and store the primary volume data in Amazon S3. They reduce local storage needs while keeping hot data nearby, unlike stored volumes that keep the full primary dataset on premises.
- S3 Storage Class Analysis // S3 Storage Class Analysis reports object access patterns to help decide whether to transition data from S3 Standard to Standard-IA; it does not move objects itself. It does not recommend One Zone-IA or Glacier as target classes.
- AWS Cost Anomaly Detection // AWS Cost Anomaly Detection uses machine learning to identify spending that is unusual relative to learned patterns and can notify subscribers. Unlike a budget alarm, it does not require a fixed spend threshold.
- AWS Cost Optimization Hub // AWS Cost Optimization Hub consolidates, deduplicates, and prioritizes cost-saving recommendations across accounts and AWS services, including idle-resource and rightsizing opportunities. It surfaces actions for review rather than automatically changing resources.
- EC2 Dedicated Hosts // An EC2 Dedicated Host is a physical server reserved for one customer and provides visibility and control over instance placement, including support for eligible server-bound software licenses. Dedicated Instances also use single-customer hardware but do not provide the same host-level placement and license visibility.
- Amazon ECS launch type pricing // With the ECS EC2 launch type, you pay for the underlying EC2 instances and attached EBS volumes, whether or not every task uses all capacity. With Fargate, billing is based on the vCPU and memory resources requested by each task for the time it runs, so there is no EC2 host fleet to manage.
- EC2 Dedicated Instances // Dedicated Instances run in a VPC on hardware dedicated to a single AWS customer, meeting single-tenant isolation without reserving an entire physical server. They are generally the lower-cost choice when host placement control and server-bound license visibility are not required; those capabilities distinguish Dedicated Hosts.
